# YouVersion Platform API Integration — Implementation Plan

_Version: v0.3.0_
_Created: 2026-04-27_
_Status: Draft_
_GitHub Issue: #6_

## Overview

Integrate the YouVersion Platform (YVP) REST API into Selah so users can read Bible translations beyond the bundled KJV. The app stays fully offline for KJV but can fetch additional translations when a YVP app key is configured. The architecture is provider-agnostic so future providers can be added alongside YouVersion.

## Current State Analysis

- KJV is the only bundled translation, embedded via `include_bytes!` into an in-memory SQLite DB
- `TRANSLATIONS` in `bible/mod.rs` is a static `&[TranslationInfo]` with 14 entries; only KJV has `offline: true`
- All data access goes through `bible/db.rs` — `get_chapter()`, `get_verse()`, `search()`, `get_random_verse()` — all take `(conn, translation, book_num, chapter)` using 1-based numeric book IDs
- `BrowserState.translation` stores a string code like `"KJV"` — the translation picker guards on `t.offline` before allowing selection
- Book identification uses 1-based `u32` book_num (1=Genesis, 66=Revelation); `books.rs` has abbreviations like `"Gen"`, `"Exod"` — neither matches USFM codes
- The YVP API uses USFM book codes (`GEN`, `EXO`, `JHN`) and numeric version IDs (e.g., 3034 for BSB)
- The YVP passage endpoint returns full chapter/passage text, not individual verse rows

### Key Discoveries

- `BrowserState::load_chapter()` at `browser.rs:252` calls `db::get_chapter(conn, translation, book_num, chapter)` — this is the primary data fetch point that needs a cache/API fallback path
- Translation selection at `app.rs:266-273` guards on `t.offline` — need to allow API-backed translations when configured
- `BookInfo` in `books.rs` has `abbreviation` field but not USFM codes — need to add `usfm` field
- YVP API auth is `X-YVP-App-Key` header (not secret per YV docs) — simple config
- YVP passage endpoint: `GET /v1/bibles/{versionId}/passages/{USFM}?format=text` returns `{ id, content, reference }`
- Passages are per-chapter max; cross-chapter ranges require multiple calls

## Desired End State

1. **Provider settings overlay**: Users can open a settings overlay, see a list of providers (initially just YouVersion), enter/edit their app key
2. **Translation picker**: Shows bundled KJV (always available) + YVP translations fetched from the API. Selecting a non-cached translation triggers a background fetch with "Loading..." indicator
3. **Cached translations**: Fetched chapters cached in a local SQLite DB with 90-day TTL
4. **USFM alignment**: `BookInfo` gains a `usfm` field mapping to YVP's 3-letter codes; all API calls use USFM
5. **Non-blocking fetch**: API calls happen on a background thread; main TUI event loop never blocks
6. **Semi-static translations**: Ship with a curated list of YVP version IDs; translation picker shows these. Future: ability to search and add new translations

### Verification

- `cargo build --features api` compiles cleanly
- `cargo build` (no features) still works — KJV-only, no network deps
- `cargo test` passes all existing + new tests
- Manual: configure app key → open translation picker → select BSB → chapter loads from API → subsequent loads hit cache

## What We're NOT Doing

- OAuth / Sign In With YouVersion (no user accounts)
- Syncing highlights/bookmarks to YouVersion
- Translation search/discovery UI (future iteration)
- Multiple simultaneous providers
- FTS5 search on API-fetched translations (only KJV search for now)

## Implementation Approach

Six phases, each independently testable:

1. **USFM alignment** — Add USFM codes to `BookInfo`, create mapping utilities
2. **Provider config model** — `config/providers.rs` + settings persistence + CLI support
3. **API client** — `api/` module with YouVersion HTTP client, feature-gated behind `api`
4. **Cache layer** — Local SQLite cache with 90-day TTL
5. **Data layer integration** — Unified data access that checks bundled DB → cache → API
6. **UI integration** — Provider settings overlay, updated translation picker, loading states

```rust
pub fn book_usfm(book_num: u32) -> &'static str {
    BOOKS.get((book_num - 1) as usize).map(|b| b.usfm).unwrap_or("UNK")
}

pub fn book_num_from_usfm(usfm: &str) -> Option<u32> {
    BOOKS.iter().position(|b| b.usfm == usfm).map(|i| (i + 1) as u32)
}
```

## Phase 5: Data Layer Integration

### Overview

Unify data access so `BrowserState::load_chapter()` transparently checks: bundled DB → cache → API fetch. API fetches are non-blocking (background thread + `mpsc` channel).

### Changes Required

#### 1. Create unified data resolver

**File**: `src/bible/resolver.rs` (new)

```rust
pub enum VerseSource {
    Bundled,   // KJV from embedded SQLite
    Cached,    // From local cache
    Fetching,  // In progress
}

pub enum FetchResult {
    Ready(Vec<Verse>),
    Loading,
    Error(String),
}
```

Resolution flow:
1. If translation is bundled (KJV) → query `db.rs` as today
2. If translation is API-backed → check cache (not expired) → return cached
3. If cache miss → spawn background thread → return `Loading`
4. Background thread: fetch from API → store in cache → send result via `mpsc::Sender`
5. Main loop polls `mpsc::Receiver` each tick → updates `BrowserState` when ready

#### 2. Add async fetch channel to `App`

**File**: `src/app.rs`
- Add `fetch_rx: Option<mpsc::Receiver<FetchResult>>` to `App`
- On each tick, check `fetch_rx.try_recv()` → update browser state
- Show "Loading {translation}..." in Scripture panel while fetching

#### 3. Update `BrowserState::load_chapter()`

**File**: `src/ui/browser.rs`
- `load_chapter()` now takes a `resolver` parameter instead of bare `Connection`
- When resolver returns `Loading`, set `self.current_chapter = None` and `self.loading = true`
- Add `pub loading: bool` and `pub loading_error: Option<String>` to `BrowserState`

#### 4. Update translation picker selection guard

**File**: `src/app.rs:266-273`
- Remove `&& t.offline` guard
- Instead: allow selection if `t.offline || self.providers.has_active_provider()`
- When selecting an API translation for the first time, trigger fetch

- HTTPS only for all API calls (enforced by `ureq` default)
- Never log or include app key in error messages
- Sanitize API responses before cache insertion
