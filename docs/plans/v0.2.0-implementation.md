# Selah v0.2.0 Implementation Plan

## Overview

Add user study features (highlights, notes, multi-verse bookmarks), improve exit UX with a confirmation dialog, and create contributor documentation. Five issues from the v0.2.0 milestone, delivered in 5 phases.

## Current State Analysis

v0.1.0 shipped 2026-04-08. The codebase has:

- 4-panel Bible reader with keyboard + mouse navigation
- 3 modal overlays via `OverlayKind` enum: `Search`, `Bookmarks`, `Translation`
- Single-verse bookmarks persisted to `bookmarks.json`
- Session persistence to `session.json`
- Double-`q` quit mechanism with `quit_pending` bool
- 5 built-in themes with semantic color tokens
- KJV bundled via `include_bytes!`

### Key Discoveries:

- `BookmarkEntry` already has an unused `note: Option<String>` field (`src/config/bookmarks.rs:14`)
- `OverlayKind` at `src/ui/browser.rs:49` is the extension point for new overlays
- All persistence uses JSON files in `directories::ProjectDirs::from("", "", "selah")?.data_dir()`
- Theme has 11 color tokens (`src/ui/theme.rs:4-16`); `highlight_bg` is already used for list selection
- Scripture rendering builds `Vec<Line>` with verse-number + text spans (`src/ui/browser.rs:451-475`)
- `quit_pending` lives on `App` (`src/app.rs:30`), not `BrowserState`

## Desired End State

Running `cargo run` launches the same TUI as v0.1.0 with these additions:

- `q` opens a confirmation dialog overlay instead of double-press quit
- `m` enters mark mode for verse range bookmarks; bookmark list shows ranges as "Book Ch:V1-V2"
- `H` cycles highlight colors on the selected verse; highlighted verses render with colored backgrounds; highlights can be toggled on/off; a Highlights List overlay browses all highlights
- `n` opens a multi-line note editor overlay for the selected verse; verses with notes show an indicator; a Notes List overlay browses all notes
- `CONTRIBUTING.md` exists at repo root with developer onboarding instructions

Verification: `cargo build --release` succeeds. `cargo test` passes. `cargo clippy -- -D warnings` clean. `cargo fmt --check` clean. All existing v0.1.0 features still work. Existing `bookmarks.json` files load without migration.

## What We're NOT Doing

- No translation API / BYOK API keys (deferred from v0.2.0, issue #6 removed from milestone)
- No cloud sync or export
- No cross-chapter verse ranges (single chapter only)
- No highlight color customization (5 preset colors only)
- No code of conduct or issue/PR templates

## Implementation Approach

Layer features bottom-up: simplest overlay first (quit confirm), then extend existing persistence (bookmarks), then add new persistence modules (highlights, notes). Documentation last since the codebase will be finalized.

## Performance Considerations

- Highlight map is rebuilt as a `HashMap` after each toggle — O(n) rebuild, O(1) lookup during render. Acceptable for expected scale (< 10k highlights).
- Notes lookup during render is O(n) per verse. For v0.2.0 this is acceptable; if it becomes slow, build a `HashSet<(String, u32, u32)>` at load time (same pattern as highlights).
- No new async or threading introduced.

## Migration Notes

- `BookmarkEntry.verse_end` uses `#[serde(default)]` — existing v0.1.0 JSON files load with `verse_end: None` automatically. No migration script needed.
- `highlights.json` and `notes.json` are new files — they simply don't exist yet and the `load()` functions return empty vectors on missing file.

## Decisions

The following decisions should be documented in `docs/decisions.md` during implementation:

### ADR-007: Notes Independent of Bookmarks

Notes use a separate `notes.json` file rather than reusing `BookmarkEntry.note`. Rationale: a user should not have to bookmark a verse to annotate it. The existing `BookmarkEntry.note` field remains available for brief bookmark labels.

### ADR-008: JSON Files for All User Data

Highlights and notes follow the same JSON-file persistence pattern as bookmarks rather than introducing a writable SQLite database. Rationale: consistency with existing code, simplicity, and the expected data scale (< 10k entries) doesn't warrant a database. A `HashMap` built at load time provides O(1) lookup where needed.

### ADR-009: Multi-Line Note Editor

The note editor supports multi-line text input with `Enter` for newlines and `Ctrl+S` to save. Rationale: single-line notes are too limiting for study insights — users need the ability to write paragraph-length reflections. This requires a more complex text editor widget (line-by-line cursor, vertical scroll, line merging on backspace at boundaries), but the value justifies the implementation cost.

### ADR-010: Highlight Visibility Toggle

Highlights can be toggled on/off globally without deleting highlight data. Rationale: users may want to read scripture without visual clutter but retain their highlights for later. The toggle state is persisted in `SessionState`.

### ADR-011: Browse Overlays for Highlights and Notes

Both highlights and notes get dedicated list overlays (similar to the existing Bookmarks overlay) for browsing and navigating to annotated verses. Rationale: as the number of highlights and notes grows, users need a way to find and revisit them without scrolling through every chapter.
