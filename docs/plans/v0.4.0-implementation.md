# v0.4.0 Implementation Plan — Menu Overlay, Version Flag, Public Distribution

## Overview

Three features bundled into one release cycle: a `--version` CLI flag (#13), a `?` tabbed menu overlay with interactive status bar (#8), and preparation for public distribution (per `docs/specs/public-distribution.md`). Phases are ordered by dependency — version flag is a prerequisite for the menu overlay (which displays it), and both must ship before the public release prep.

## Current State Analysis

- **CLI:** `src/cli.rs` uses clap derive but has no `#[command(version)]` attribute — `selah --version` is unsupported.
- **Status bar:** `src/ui/browser.rs:595-604` shows a long inline keybinding string that's already too crowded.
- **`?` key:** Currently replays the splash/banner (`src/app.rs:596-598`). Will be repurposed for help overlay; splash replay will be removed entirely.
- **Overlay pattern:** 8 overlays follow the same pattern — `OverlayKind` variant in `src/ui/browser.rs:57-66`, a render function in `src/ui/<name>.rs`, key handling in `src/app.rs:162-542`, and routing in `src/ui/browser.rs:607-631`.
- **Distribution:** cargo-dist is configured (`dist-workspace.toml`), CI release workflow exists (`.github/workflows/release.yml`), Homebrew tap is private at `jeremycastanza/homebrew-selah-tap`. The spec at `docs/specs/public-distribution.md` defines an 8-phase audit process.

### Key Discoveries

- `src/app.rs:596-598` — `?` maps to `AppMode::Banner(BannerState::new())`; this line gets replaced.
- `src/ui/browser.rs:598` — Status bar text: `"q: quit | /: search | b: bookmark | H: highlight | n: note | r: random | S: settings | ?: splash"`
- `src/ui/settings.rs` — Cleanest overlay template to follow (simple state, bordered modal, `Clear` widget, themed styles).
- `Cargo.toml:3` — Current version is `0.3.1`; will bump to `0.4.0` for this release.
- `dist-workspace.toml:24` — `publish = false` on Homebrew tap; must flip to `true` for public distribution.

## Desired End State

After this plan is complete:
1. `selah --version` prints `selah 0.4.0`
2. Pressing `?` in the browser opens a tabbed menu overlay with 4 sections (Navigation, Actions, App, Overlays), switchable via keyboard (`Tab`/`h`/`l`) or mouse click on tabs
3. The status bar shows `? Menu │ KJV │ Dark` — each segment is clickable (menu → opens overlay, translation → opens picker, theme → cycles)
4. Both repos (`selah` and `homebrew-selah-tap`) are audited, hardened, and ready to flip to public visibility

### Verification:
- `cargo build` succeeds
- `cargo test` passes (if tests exist)
- `cargo clippy` has no warnings
- `selah --version` outputs version
- Menu overlay opens with `?`, tabs switch with `Tab`/`h`/`l` or mouse click, scrolls with `j`/`k`, closes with `Esc`/`?`
- Status bar segments are clickable: menu → overlay, translation → picker, theme → cycle
- `gitleaks detect` clean on both repos
- All Phase 8 checklist items from the public-distribution spec pass

## What We're NOT Doing

- Adding new keybindings or features beyond help/version
- Changing the splash/banner screen itself (just removing the `?` shortcut to replay it)
- Rewriting the release CI workflow (only config changes in `dist-workspace.toml`)
- Actually making the repos public (this plan prepares for it; the flip is a manual step)
- Adding x86_64 build targets (out of scope)

## Implementation Approach

Phase 1 is a one-line clap attribute addition. Phase 2 follows the established overlay pattern with extensions: new `OverlayKind::Help` variant, new `src/ui/help.rs` with tabbed layout and click-region tracking, key + mouse handling in `app.rs`, simplified status bar with clickable segments. Phase 3 follows the spec at `docs/specs/public-distribution.md` sequentially.

### Changes Required

## Phase 2: Menu Overlay, Status Bar & Mouse Interactivity (#8)

### Overview

Replace the `?` splash replay with a new tabbed menu overlay and simplify the status bar to show only essential info. The overlay uses a 4-tab layout (Navigation, Actions, App, Overlays) switchable via keyboard or mouse click. The status bar segments (`? Menu`, translation, theme) are each clickable to open the corresponding overlay or toggle the theme.

### Changes Required

#### 1. New overlay variant

**File:** `src/ui/browser.rs`
**Change:** Add `Help(HelpState)` to the `OverlayKind` enum. Add import for the new module.

```rust
pub enum OverlayKind {
    // ...existing variants...
    Help(HelpState),  // new
}
```

#### 2. New menu UI module

**File:** `src/ui/help.rs` (new file)
**Purpose:** Render function and state for the menu overlay.

Pattern follows `src/ui/settings.rs`:
- `HelpState` struct with `scroll: u16`, `active_tab: usize`, `tab_bar_rect: Rect`, and `tab_offsets: [u16; 4]`
- `tab_at_col(col)` method — returns which tab index a given column falls on (for mouse clicks)
- `render_help(frame, area, &mut state, theme)` function (takes `&mut` to store tab geometry)
- Centered modal (70% width, 70% height) with `Clear` + bordered block
- Title: `" Menu "`, bottom: `" Tab/h/l: switch  j/k: scroll  Esc: close "`
- Tab bar at top with 4 labeled tabs separated by `│`; active tab is accent/bold/underlined
- Content area below shows keybindings for the active tab only
- Scroll support using `Paragraph::scroll((state.scroll, 0))`

Tab content:

| Tab | Keybindings |
|-----|-------------|
| **Navigation** | `h/←` prev panel, `l/→/Enter` next panel, `j/↓` down, `k/↑` up |
| **Actions** | `/` search, `b` bookmark, `B` list, `H` highlight, `g` toggle visibility, `G` list, `n` note, `N` list, `r` random, `v` translation |
| **App** | `t` theme, `S` settings, `?` menu, `q` quit |
| **Overlays** | `Esc` close, `j/k/↑/↓` navigate, `Enter` select, `d` delete |

#### 3. Register the module

**File:** `src/ui/mod.rs`
**Change:** Add `pub mod help;` to the module declarations.

#### 4. Wire up keybinding in app

**File:** `src/app.rs`
**Changes:**
- Replace `?` handler — instead of `AppMode::Banner`, open the menu overlay:
  ```rust
  KeyCode::Char('?') => {
      state.overlay = Some(OverlayKind::Help(HelpState::default()));
  }
  ```
- Add menu overlay key handling in the overlay match block:
  ```rust
  Some(OverlayKind::Help(help)) => match key {
      KeyCode::Char('j') | KeyCode::Down => help.scroll += 1,
      KeyCode::Char('k') | KeyCode::Up => help.scroll -= 1,
      KeyCode::Tab | KeyCode::Char('l') | KeyCode::Right => { next tab, reset scroll },
      KeyCode::BackTab | KeyCode::Char('h') | KeyCode::Left => { prev tab, reset scroll },
      KeyCode::Esc | KeyCode::Char('?') => close,
      _ => {}
  },
  ```
- Add import for `HelpState` from `crate::ui::help`.

#### 5. Route overlay rendering

**File:** `src/ui/browser.rs`
**Change:** Add the `Help` arm to the overlay render match:
```rust
OverlayKind::Help(h) => render_help(frame, area, h, theme),
```
Add import: `use crate::ui::help::{HelpState, render_help};`

#### 6. Simplify the status bar

**File:** `src/ui/browser.rs`
**Change:** Replace the status bar text with `"? Menu"`. The format line already appends `│ {translation} │ {theme_label}`, so the result will be: `? Menu │ KJV │ Dark`.

#### 7. Clickable status bar segments

**File:** `src/ui/browser.rs`
**Change:** Add `status_rect: Rect`, `status_menu_end: u16`, `status_translation_end: u16` fields to `BrowserState`. Compute segment boundaries during render based on the formatted status text.

**File:** `src/app.rs`
**Change:** In `handle_mouse`, before delegating to `BrowserState`, check if a left-click falls within the status bar:
- Click on menu segment (`col < status_menu_end`) → open Menu overlay
- Click on translation segment (`col < status_translation_end`) → open Translation picker
- Click on theme segment (remainder) → cycle theme via `self.theme_name.next()`

#### 8. Clickable menu overlay tabs

**File:** `src/ui/help.rs`
**Change:** `render_help` stores `tab_bar_rect` and `tab_offsets` in `HelpState` each frame. `tab_at_col()` resolves a column to a tab index.

**File:** `src/app.rs`
**Change:** In `handle_mouse`, before the generic overlay-blocks-mouse guard, check if the Help overlay is open and a left-click falls on the tab bar. If so, switch `active_tab` and reset scroll.

## Phase 3: Public Distribution Preparation

### Overview

Execute the audit and hardening spec at `docs/specs/public-distribution.md` to prepare both `selah` and `homebrew-selah-tap` repos for public visibility. This phase is subdivided into the spec's 8 sub-phases.

### Changes Required

#### 3a. Secret & Credential Scan (Spec Phase 1)

- Install `gitleaks` if not present
- Run `gitleaks detect --source . --verbose --report-path gitleaks-report.json` on **both repos**
- Classify all findings as true/false positives
- Document true positives (do NOT commit the report)
- **Pause and report findings** — credential rotation requires human action

#### 3b. History Rewrite (Spec Phase 2)

- Only if Phase 3a found true positives
- Use `git filter-repo` to redact secrets
- Re-run gitleaks to verify clean history
- **Requires human confirmation** before force-push

#### 3c. Working Tree & Tracked File Audit (Spec Phase 3)

- Review `git ls-files` output for sensitive files
- Verify `.gitignore` is comprehensive (check for `.env`, `*.pem`, `*.key`, `*.sqlite`, `*.db`, `.DS_Store`)
- Remove any tracked sensitive files with `git rm --cached`

#### 3d. CI/CD & GitHub Actions Hardening (Spec Phase 4)

- Audit `.github/workflows/release.yml`:
  - Verify no hardcoded secrets
  - Check for dangerous triggers (`pull_request_target`)
  - Pin third-party actions to full commit SHAs
  - Add explicit `permissions:` blocks
- Document recommended GitHub UI settings to apply post-publicize

#### 3e. Homebrew Tap Audit & Migration (Spec Phase 5)

- Rename `homebrew-selah-tap` → `homebrew-selah` (GitHub UI — manual step)
- Update `dist-workspace.toml`: `tap = "jeremycastanza/homebrew-selah"`, `publish = true`
- Rewrite formula to use public release URLs (no auth headers)
- Update tap README to remove PAT instructions
- **Verify:** clean `brew install` without `HOMEBREW_GITHUB_API_TOKEN`

#### 3f. Repository Metadata & Open-Source Readiness (Spec Phase 6)

- Verify `LICENSE` file exists (MIT per `Cargo.toml:6`)
- Add `SECURITY.md` with responsible disclosure instructions
- Review and update `CONTRIBUTING.md`
- Review `README.md` — remove internal references, add badges

#### 3g. Branch Protection & Repository Settings (Spec Phase 7)

- **Applied after repos go public** (GitHub Free limitation)
- Document rulesets to apply for both repos
- Configure GitHub Actions permissions and fork PR approval settings

#### 3h. Final Verification (Spec Phase 8)

- Run the full checklist from the spec
- Verify gitleaks clean, all credentials rotated, `.gitignore` comprehensive
- Verify CI workflows use secrets correctly, actions pinned to SHAs
- Verify tap formula works with public URLs
- Verify all metadata files present
